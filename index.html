1. What this page is for

FleetAvail is intended to move from telemetry to model predictions, then from predictions to maintenance decisions and finally to fleet availability. The existing repository already has the C-MAPSS baseline and a runnable synthetic dashboard. The multi-model architecture is still a target and is not being represented as already trained or production-ready.

3. Detailed change log — changes implemented in this work

Feature 1 — C-MAPSS model provider boundary
File: ml/cmapss/providers.py

What it is: A small adapter around the existing trained C-MAPSS RUL model.

Simple meaning: Instead of the API needing to know how the model was trained or saved, it can ask a provider for a prediction.

What it does: Loads a .joblib C-MAPSS model, accepts one preprocessed temporal sequence with shape [window, features], calls the trained model and returns a non-negative RUL prediction.

Relationship: It sits between the C-MAPSS model artifact and the future real-time inference layer. Later XGBoost, Isolation Forest, LSTM and TCN providers can use the same architecture.

Important: Adding this adapter does not mean the repository now has a trained model artifact or real aircraft model inference.

Feature 1 — Optional fused provider + safe fallback
File: ml/cmapss/providers.py

What it is: FusedPredictionProvider provides a transition layer between the current heuristic system and future trained models.

Simple meaning: The project can keep running even when there is no trained model file yet, while giving us a clean place to plug the real RUL result in.

Relationship: It uses the existing ml/health.py fusion function. Later, XGBoost failure risk and Isolation Forest anomaly outputs can be injected into the same flow.

Metadata: The provider now returns a model_version value so model provenance can eventually be exposed through the API.

Contract upgrade — sequence-aware PredictionProvider
File: ml/model_contract.py

What it is: The prediction contract was changed from scalar feature-only input to allow an optional temporal sequence.

Simple meaning: A future LSTM/TCN or C-MAPSS temporal model needs a history of sensor readings, not just one row. The contract now allows that history.

Relationship: This is the interface between telemetry buffering, preprocessing, models and the API.

New field: Prediction.model_version defaults to "unknown" so existing consumers do not break.

Provider unit test
File: ml/cmapss/providers_test.py

What it is: A small deterministic test using a stub model.

Simple meaning: It proves the provider sends exactly one 30-cycle, 2-feature sequence to a model and correctly reads the returned RUL.

Why this matters: We can validate the adapter without needing the NASA dataset or expensive training.

Implementation roadmap
File: docs/roadmap.md

What it is: A stage-by-stage implementation plan covering the complete FleetAvail system.

Simple meaning: It prevents us from implementing the frontend or optimizers before the model outputs and decision data are stable.

Relationship: It defines the order: provider → sequence buffer → XGBoost → Isolation Forest → Health Fusion → LSTM/TCN → real-time inference → digital twin → maintenance optimizer → spare allocation → fleet availability → MLOps → final frontend.

Feature 2 — 30-cycle telemetry sequence buffer
Files: ml/sequence_buffer.py and tests/test_sequence_buffer.py

What it is: A bounded in-memory history for telemetry samples, independently keyed by aircraft and component.

Simple meaning: The system remembers the latest 30 readings for one aircraft component instead of treating every reading as an isolated value.

What it does: Validates identifiers and numeric finite sensor values, requires strictly increasing cycle numbers, retains only the latest window_size samples, reports whether a full window exists, returns chronological samples, and converts a complete window into a float32 NumPy array in the requested feature order.

Relationship: This is the input-side foundation for the C-MAPSS provider and future LSTM/TCN inference. It deliberately does not scale data, engineer features, run models, or change the FastAPI behavior yet.

Tests: Covers rolling-window limits, aircraft/component isolation, feature ordering and array shape, duplicate/out-of-order rejection, invalid values, and incomplete-window handling.

Feature 3 — XGBoost failure-risk model
Files: ml/cmapss/failure_risk.py, scripts/train_failure.py, scripts/predict_failure.py, tests/test_failure.py

What it is: A supervised classifier that estimates the probability that an engine is inside a defined failure-risk horizon.

Simple meaning: Instead of only asking “how many cycles are left?”, the system can also ask “how likely is failure within the next N cycles?”

Failure definition: A row is labeled failure_within_horizon=1 when its RUL is less than or equal to the configured horizon. The default training horizon is 30 cycles.

Validation: Engine trajectories are split as complete units into train, calibration and holdout sets. Individual rows from one engine are never spread across those splits.

Model: XGBoost's binary classifier is trained with class-imbalance weighting. Probabilities are then calibrated with a sigmoid/Platt calibrator fitted only on the held-out calibration engines.

Outputs: Calibrated failure probability, configurable classification threshold, ROC-AUC, average precision, Brier score, log loss, precision, recall and F1.

Persistence: The model is saved as .joblib; metadata stores the dataset, horizon, feature schema, temporal windows, split fractions, threshold and evaluation results.

Relationship: This is the failure-risk branch alongside the RUL branch. It is intentionally not connected to FastAPI yet; real-time model orchestration comes later after the remaining model branches are established.

Tests: Covers horizon labeling, engine isolation, calibrated probabilities, model save/load round-trip and threshold-aware metrics.

Feature 5 — Formal Health Fusion
File: ml/health.py

What it is: A typed state machine for converting model signals into an operational component state.

Simple meaning: The system no longer has only a numeric health score. It also says whether the component is NORMAL, WATCH, DEGRADED or CRITICAL and explains why.

What it does: Validates inputs, preserves the existing score weighting, classifies the operational state and adds explicit reason codes for risk, RUL, anomaly, health, data quality and confidence.

Relationship: It is the decision boundary between independent ML branches and downstream maintenance/twin logic.

Tests: tests/test_health_fusion.py.

Feature 8 — Persistent Digital Twin lifecycle state
File: digital_twin/state.py

What it is: Persistent aircraft/component state plus lifecycle events.

Simple meaning: The system remembers what it knows about an aircraft instead of losing the state after every prediction.

Persistence: The prototype uses an atomic local JSON file by default. The store API is backend-neutral so PostgreSQL/Redis can replace it later.

Events: Prediction updates and maintenance actions are retained with timestamps and cycles.

Tests: tests/test_decision_layers.py.

Feature 9 — Constraint-aware maintenance optimizer
File: decision_engine/maintenance_optimizer.py

What it is: A deterministic maintenance planning layer.

Simple meaning: It ranks work by risk and RUL urgency, then puts work into a finite maintenance schedule.

Constraints: Planning horizon, daily maintenance-hour capacity and spare availability are represented explicitly.

Outputs: Action, priority score, scheduled day, duration, spare part and reason codes.

Tests: tests/test_decision_layers.py.

Feature 10 — Constrained spare allocation
File: decision_engine/spares.py

What it is: Inventory allocation across competing maintenance requests.

Simple meaning: A part cannot be given to everyone when only a limited number exists. Higher-priority compatible requests are served first and unmet demand is reported.

Tests: tests/test_decision_layers.py.

Feature 11 — Fleet availability projection
File: decision_engine/fleet_availability.py

What it is: Current and projected fleet readiness calculation.

Simple meaning: It estimates how many aircraft are available now and how many can recover within the planning horizon after feasible maintenance and spare decisions.

Outputs: Current/projected availability percentages, blocked aircraft and recoverable aircraft.

Tests: tests/test_decision_layers.py.

C-MAPSS raw-data directory structure
Files: data/raw/cmapss/.gitkeep and data/raw/cmapss/FD001/.gitkeep

What it is: Repository placeholders for the required NASA C-MAPSS dataset location.

Simple meaning: Git now preserves the folder structure even though the actual dataset is not committed.

Required FD001 files: train.txt, test.txt, RUL_test.txt.

Relationship: The training scripts already read this location, so the provider can later load a model trained from that pipeline.

6. How to check each implemented feature

Features 5 and 8–11 — decision layers

pytest -q tests/test_health_fusion.py
pytest -q tests/test_decision_layers.py
pytest -q tests/test_api_decision_layers.py

These checks cover typed health fusion, persistent twin state, maintenance scheduling, spare constraints, fleet availability, and the new FastAPI endpoints.

Feature 3 — Test the XGBoost failure-risk model

pytest -q tests/test_failure.py

Expected: all four failure-risk tests pass.

After the NASA FD001 files are present, train the model with:

python scripts/train_failure.py --subset FD001 --horizon 30

Then inspect terminal-engine predictions and evaluation metrics with:

python scripts/predict_failure.py --subset FD001

The trained artifacts are written to models/cmapss/fd001_failure.joblib and models/cmapss/fd001_failure.json. Training and numerical metrics require the actual C-MAPSS files and are not claimed here unless run on those files.

Feature 2 — Test the telemetry sequence buffer

pytest -q tests/test_sequence_buffer.py

Expected: all five sequence-buffer tests pass.

The tests prove that the buffer keeps only the latest window, isolates aircraft/component histories, preserves chronological order, returns the expected float32 shape, rejects duplicate/out-of-order cycles, rejects non-finite values, and blocks full-window access until enough samples exist.

A. Check the provider without training

Run this from the repository root after dependencies are installed:

The provider unit test is the recommended deterministic check because it exercises the exact provider boundary without requiring NASA data or a trained artifact.

pytest -q ml/cmapss/providers_test.py

Expected result: one provider test passes.

B. Check the contract

python -c "from ml.model_contract import Prediction; p=Prediction(10,0.2,0.1,0.9,1.0); print(p)"

Expected: the printed object contains model_version='unknown'.

C. Train the current C-MAPSS baseline

python scripts/train_cmapss.py --subset FD001 --window 30

This requires the three FD001 NASA files. It should create:

models/cmapss/fd001_rul.joblib
models/cmapss/fd001_rul.json

D. Run terminal prediction

python scripts/predict_cmapss.py --subset FD001

This uses the trained artifact and prints predicted RUL per test engine.

E. Check the full existing application

python -m uvicorn backend.app.main:app --reload --port 8000

Then open:

http://127.0.0.1:8000/
http://127.0.0.1:8000/docs
http://127.0.0.1:8000/health

The current dashboard remains heuristic/synthetic; training the C-MAPSS model alone does not automatically replace the API provider yet.

F. Run the repository tests

pytest -q

This is the final local verification command after installing the project's Python dependencies.

11. Important distinction: code vs. trained results

Do not confuse implementation with model validation. The code for the leakage-aware C-MAPSS pipeline exists, but a model artifact is not stored in Git. Numerical MAE/RMSE/NASA-score results should only be reported after running the training and evaluation command on the actual dataset. Example values in project documentation are not measured FleetAvail results.

12. Definition of done

The final demonstration should be able to show one continuous chain:

Telemetry
  ↓
30-cycle real sequence
  ↓
RUL + failure risk + anomaly
  ↓
Fused component health
  ↓
Aircraft digital-twin update
  ↓
Maintenance recommendation
  ↓
Constrained spare allocation
  ↓
Fleet optimization
  ↓
Projected fleet availability
  ↓
Dashboard explanation + audit trail

The strongest final demonstration is a degradation scenario where the system detects the problem, explains the health change, predicts the consequence, schedules maintenance, allocates a constrained spare and shows the resulting effect on fleet readiness.
